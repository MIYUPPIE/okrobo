# Decision: CAD Kernel — Phase 7.2 (live-recompute executor)

**Date:** 2026-09-06

## Scope

Per the roadmap laid out in `cad-kernel-feature-tree-data-model.md`, Phase 7.2 is "the real hard part: reimplement fillet/chamfer/shell/draft/cut against raw OpenCascade builders... build the executor that replays a whole feature list, propagating identity step to step." This delivers exactly that — a new module, `apps/studio/src/cad/executor.ts` — and stops there. It does **not** wire anything into the UI, does not detect or react to an edit, and does not implement "recompute everything downstream of step K." Nothing in this codebase can edit a stored `Feature` yet (7.1 shipped write-only history); inventing that orchestration now, ahead of 7.3's own real UI requirements, risks building the wrong shape. What 7.2 delivers is the concrete, thoroughly-tested *primitive* 7.3 will build that orchestration on top of: given one operation's own raw OpenCascade builder, correctly answer "what happened to this specific edge/face after applying it."

## Why raw builders: replicad's own convenience wrappers destroy the evidence

Verified by reading replicad's own source (`node_modules/replicad/dist/casting-*.cjs`): `Shape3D.fillet()`/`.chamfer()`/`.shell()`/`.draft()` each construct a raw OpenCascade builder (`BRepFilletAPI_MakeFillet`, `BRepFilletAPI_MakeChamfer`, `BRepOffsetAPI_MakeThickSolid`, `BRepOffsetAPI_DraftAngle`), call it, extract the result shape, and let the builder go out of scope — its `Modified()`/`Generated()`/`IsDeleted()` history (all inherited from `BRepBuilderAPI_MakeShape`, confirmed by reading `replicad-opencascadejs`'s own generated `.d.ts`) is never read by replicad and never exposed to a caller. `executor.ts` reimplements each operation's exact same OpenCascade call sequence directly against `getOC()` (replicad's own public export — no fork needed, matching `Shape3D`'s own public `.wrapped` getter and the public `downcast()`/`Edge`/`Face`/`Solid` constructors, all of which turned out to be exactly what's needed with zero private-API reaching-in). The result: `replayFeatures`'s own fillet_chamfer/shell/draft output is byte-identical to calling `kernel.ts`'s own single-shot `fillet()`/`shell()`/`draft()` — verified directly in `executor.test.ts` — while the builder itself survives long enough to answer history queries before being disposed.

Cut is the one exception: it carries no picks, so there's nothing to harvest history for. `applyCut` just calls replicad's own public `Shape3D.cut()` (still a real, live B-rep boolean — see below).

## The real finding: `Modified()`/`Generated()`/`IsDeleted()` behave differently per operation family, and per KIND

Verified empirically against real OpenCascade WASM (all five operations — fillet, chamfer, cut, shell, draft), not assumed:

1. **Local operations lie about deletion, silently.** `BRepFilletAPI_MakeFillet`/`MakeChamfer` and `BRepOffsetAPI_DraftAngle` only ever record history for the specific entities their own operation touched. Querying `IsDeleted()` for an edge/face nowhere near the operation returns **`true`**, with both `Modified()` and `Generated()` empty — even though that entity plainly survives, completely unchanged, in the result. `IsDeleted() === true` is *not* evidence of removal for these builders; it just means "no history was tracked for this, because it wasn't relevant." The correct read for an empty-history entity is a plain geometric `.near()` re-match against the operation's own output (exactly the mechanism Phase 5/6 already established) — which reliably finds it.
2. **Shell's own "removed" face isn't gone — it's a rim.** Passing a face to `BRepOffsetAPI_MakeThickSolid` as "to remove" (the opening) does *not* leave it untracked: `Modified()` returns one real, geometrically meaningful face — the thin rim connecting the opening's outer boundary to the offset inner wall (verified: for a 1×1×1 box shelled at 0.05 thickness, the "removed" face's `Modified()` entry has area 0.19, exactly `1 - (1 - 2×0.05)²`, and sits at the same location the removed face did). Trusting `Modified()` here (not falling back to `.near()`, which is not guaranteed to find a small rim) is what correctly answers "this face's own single successor."
3. **A boolean cut tracks everything, touched or not.** `BRepAlgoAPI_Cut` (used by replicad's own `Shape3D.cut()`) returns a real `Modified()` entry for essentially every face in the target, whether or not the tool actually intersected it — consistent with the same history-first read, no `.near()` fallback ever needed in practice.
4. **A genuinely fully-consumed entity resolves to nothing, by every measure.** Verified directly: a cut tool that entirely engulfs a target face gives empty `Modified()`/`Generated()`, `IsDeleted() === true`, *and* no geometric match in the result either. This is the one case that should — and does — report `"deleted"`.
5. **A candidate's own *kind* is not guaranteed to match the original entity's kind.** Filleting or chamfering an edge does not produce a successor *edge* — `Generated()` on the target edge returns a **face** (the new blend/bevel surface the edge became). Constructing `new Edge(candidate)` on that would just be wrong; `resolveAfterOperation`'s own `pointOfRawShape` checks the *candidate's* real `ShapeType()` (via replicad's own public `downcast()`, since Embind's own binding runtime rejects a plain `TopoDS_Shape` passed where a `TopoDS_Edge`/`TopoDS_Face` is expected — a real, not merely TypeScript-level, type check) and reads whichever kind it actually turned out to be.

`resolveAfterOperation(builder, original, originalPoint, kind, output, tolerance)` encodes all five findings: history-first when `Modified()`/`Generated()` yield anything (closest candidate by point distance, if more than one), a `.near()`-against-the-output fallback otherwise, `"deleted"` only when both come up empty. It's exported specifically for direct testing against hand-built raw-OpenCascade scenarios (`executor.test.ts` exercises all three outcomes independently of the higher-level `replayFeatures` API), the same "exposed for tests, not for UI" posture `kernel.ts`'s own `*Mesh`-suffixed synchronous functions already establish.

## The executor keeps the whole chain in live B-rep — Cut included

`replayFeatures(features: Feature[])` walks a body's own recorded history (contract v2, Phase 7.1) and keeps a *single* live `Shape3D` alive across every step — the previous step's own output feeds directly into the next step's operation, never round-tripping through a baked mesh mid-chain. This is what makes Cut, inside the executor, a real B-rep boolean (`Shape3D.cut()`) rather than `cutMesh`'s own Manifold mesh-boolean-via-STL-roundtrip: the executor's own "target" for a cut step is always the previous step's still-live solid, so there's no need to reconstruct a mesh-native shape from baked triangle data the way the standalone Cut creators still must (their own target can be *any* existing body, `cad_mesh` included — a capability the executor's own root-replay approach doesn't have, and isn't trying to replace). `cutMesh`/`geometryToMesh` and the three standalone Cut creators are untouched by this phase.

Verified: replaying a body's own recorded `features[]` produces the exact same mesh independently calling each existing single-shot `kernel.ts` function in sequence would (root, fillet_chamfer, shell, draft each cross-checked byte-for-byte in `executor.test.ts`; cut checked for sane non-degenerate output, since it's a genuinely different algorithm from `cutMesh`'s own Manifold path and isn't expected to match it bit-for-bit).

## `resolvedPicks`: exercised now, orchestrated later

Every modifier step's own `FeatureStepResult.resolvedPicks` records, for each of *that step's own* picks (in the same order as `feature.picks`), what `resolveAfterOperation` says happened to it once the step's own operation ran. Since nothing edits a `Feature[]` yet, every real call through `replayFeatures` only ever resolves a pick against the very operation that just consumed it — which, empirically, is essentially always `"ok"` (a picked edge/face is definitionally what that operation acted on). The genuinely interesting case — a *downstream* feature's pick, after an *upstream* feature was edited — has no reachable trigger yet (7.3's own scope: detecting an edit, deciding what "recompute" means for the UI, deciding how a `"deleted"` pick surfaces to the student). What 7.2 hands 7.3 is the exact primitive that question will need, proven correct against real OpenCascade for all five operations.

## Non-goals

- **No editing.** Nothing constructs a modified `Feature[]` from a UI action; that's 7.3.
- **No "recompute downstream of step K" orchestration.** `replayFeatures` replays a *whole* list top to bottom; it doesn't yet accept "start from step K with these new params."
- **No change to any existing single-shot `kernel.ts` function, `cadClient.ts`, `worker.ts`, or any creator/editor component.** `executor.ts` is additive and currently unreferenced by the shipped app — confirmed via `npm run build` (843 modules, byte-identical WASM asset sizes to Phase 7.1's own build).
- **No change to Cut's own standalone-creator behavior** (still Manifold-mesh-based, still able to target any existing body).

## Verification

`apps/studio`: `npm run typecheck`, `npm run test` (615 passed across 62 files — 15 new in `executor.test.ts`, real OpenCascade WASM, no mocks, matching `extrude.test.ts`'s own established "real pipeline" posture and 30s per-test timeout for the cold WASM load), `npm run build` (843 modules, WASM assets byte-identical in size to before this phase — confirms `executor.ts` is additive and currently tree-shaken out of the shipped bundle). No Python/C++/contract changes this phase — `Feature`/`CadPick` are consumed as already-shipped v2 types, nothing about their own shape changed.
