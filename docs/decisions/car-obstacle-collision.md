# Decision: real obstacle collision for the Car

**Date:** 2026-09-10

## Scope

User observed the car can drive straight through obstacle boxes. Confirmed by reading the engine directly: `engine/src/world.cpp`'s `World::step` only clamped position against the arena's *outer walls* — obstacle boxes placed inside the arena never physically stopped the body. They only fed the ray-cast distance/lidar sensor and, independently, the Competition Arena scoring penalty (`apps/studio/src/compete/score.ts`'s `avoid_obstacle_collision`). This was true before this session touched anything — `world.hpp`'s own `Obstacle` struct comment ("the robot can see and **bump into**") already implied physical collision was the original intent, never finished. User asked for it to be added; confirmed first that this was a real engine change, not a UI issue, before scoping it.

## Two implementations, one algorithm — both had to change

`engine/src/world.cpp` is not the only place this logic lives. `runtime/python/okrobo/_sim.py`'s `World.step` is the *reference* implementation (`world.hpp`'s own docstring: "Reference spec: runtime/python/okrobo/_sim.py"), and `engine/tests/parity/parity.mjs` locks the two together tick-by-tick at 1e-9 tolerance against a shared scenario. `runtime/python/tests/test_sim.py` states outright: "Mirrors engine/tests/test_world.cpp." Both files got the identical algorithm, in the identical place in `step()` (after the kinematic position update, before the existing wall clamp).

## The algorithm: circle-vs-AABB push-out, not an inflated-box clamp

For each obstacle: find the closest point on the box to the robot's centre (`clamp(pose, box_min, box_max)` per axis — the same construction `score.ts`'s own `circleIntersectsAabb` already uses for the scoring penalty, and the standard closest-point-on-AABB formula). If that point is within `robot_radius`, push the robot back to exactly `robot_radius` away from it, along the vector from the closest point to the robot's centre. This is the textbook circle-vs-AABB resolution and is exact at corners — a simpler-looking alternative (inflate the box by `robot_radius` and clamp x/y independently, the same style the wall clamp already uses) would resolve a diagonal approach toward a corner *incorrectly*, since a rectangle inflated on all sides is not the true Minkowski sum of a circle and a box (that shape has rounded corners). Verified directly: `test_obstacle_corner_approach` (both `test_world.cpp` and `test_sim.py`) drives straight at a box's corner and asserts the rest position sits exactly `robot_radius` from that corner point, along the diagonal — not clamped to one edge or the other.

A degenerate case is handled explicitly: if the robot's centre is already exactly at the closest point (distance zero — only reachable if it spawned inside an obstacle, since `dt` is small and student-commandable speeds are bounded), the push direction falls back to away-from-the-box's-own-centre, then to an arbitrary fixed direction if even that's degenerate. Never divides by zero, never produces NaN.

Obstacles resolve sequentially, mutating position in place, so a later obstacle in the same tick sees the already-corrected position from an earlier one. Not a general physics solver — an acceptable simplification at this engine's existing level of fidelity, and no obstacle placement in any shipped competition (including the two new C4 ones, whose clearances were hand-verified) sits close enough to another for this to matter.

## `score.ts` needed no changes

`avoid_obstacle_collision`'s own overlap check (`circleIntersectsAabb`) is an independent computation, already correct, and composes with real physical blocking without modification: the edge-triggered hit-counting (one penalty per *continuous* overlap, not per tick) still fires exactly once when the robot first touches an obstacle, whether or not it's now also physically stopped there. A robot resting against an obstacle no longer accumulates additional score penalties than it did before — driving further into something you're already touching was never possible to begin with once physically blocked.

## `collided` is instantaneous, not "resting state" — a real gotcha caught while adding studio-level test coverage

The flag (both `World::collided()`/`self._collided`) is recomputed fresh every tick from *this tick's* clamping, never latched. Driving continuously into an obstacle (or a wall) keeps it `true` every tick, because the kinematic step keeps trying to move further in and the clamp keeps re-firing. But once a caller stops commanding velocity (as `ProgramRunner`'s own `forward()` does the moment its fixed duration elapses — it is a blind, time-based move with no sensor/collision awareness of its own, so the *only* thing that can make its actual stopping position differ from "start + speed × duration" is this same engine-level clamp), the robot sits motionless exactly on the boundary; the clamp condition (`dx² + dy² < robot_radius²`, a strict `<`) is no longer true at that exact resting distance, so `collided` reads `false` on every subsequent tick even though the robot is still touching the obstacle. `apps/studio/src/program/ProgramRunner.test.ts`'s new obstacle-stop test deliberately does **not** assert `collided` for this reason (matching the pre-existing wall-stop test's own convention, which never asserted it either) — the instantaneous-collision claim is proven directly, during continuous driving, by the engine-level `test_obstacle_stop` instead.

## Verification

`ctest` (13/13, engine — 3 new obstacle cases: straight stop, driving past unaffected, diagonal corner approach), `pytest` (`runtime/python`, 223 passing + 1 pre-existing skip — the identical 3 mirrored cases), `node engine/tests/parity/parity.mjs` after a WASM rebuild (car scenario extended with a real drive-into-the-shipped-arena's-own-red-box phase — 2037 states now compared, max diff 8.88e-16, still well under the 1e-9 tolerance: C++ and Python compute *identical* trajectories through the new code path, not just individually-plausible ones). `apps/studio`: `npm run test` (913 passing — one pre-existing test, "forward stops early at the wall," needed its own fixture updated since the shared default arena has a real obstacle directly ahead of the default start pose that now blocks it before the wall; fixed by turning the robot to face a genuinely obstacle-clear direction for that specific test, and adding a new test asserting the obstacle-stop position specifically), `npm run typecheck`, `npm run build`. `./scripts/check-studio-e2e.sh` — full existing suite green twice in a row, confirming no regression anywhere else in the app. A direct check against the exact production WASM artifact (`apps/studio/src/generated/okrobo_engine.js`, loaded in plain Node the same way `parity.mjs` already does) drove the shipped Arena's own car straight for 10 simulated seconds and confirmed it stops at x=1.4999999999999998 (0.1 m short of the red box's near edge, `collided=true`) instead of reaching the far wall at x=1.9 — concrete, real-artifact proof, not a mock.

## Non-goals

- No change to MuJoCo-based physics (Robot Builder's built robots, the Arm's grasp object) — those already have real rigid-body collision via MuJoCo.
- No change to the Drone — its own separate `DroneWorld` class deliberately flies above ground obstacles (`_sim.py`'s own comment: "It flies above the ground-level obstacles... only the arena walls are a hazard").
- No general-purpose physics solver (no restitution, no momentum transfer, no simultaneous multi-obstacle resolution beyond sequential per-obstacle push-out) — this remains a simple, predictable educational simulator, matching the fidelity level of every other part of this engine.
