# Decision: robot builder programming (Robot Builder Phase 6)

**Date:** 2026-09-04

## Choice

Give a built robot (`contracts/robot-def/v0`) the ability to be driven by a written program in Test mode, the way Car/Arm/Drone already are in Simulate mode -- but addressed by the student's own actuator/sensor string ids, not a fixed, hardcoded vocabulary. New `apps/studio/src/program/BuiltProgramRunner.ts` (`BuiltRobotApi`/`BuiltProgramRunner`) and two new Blockly blocks (`okrobo_built_set_actuator`, `okrobo_built_read_sensor`) execute for real, in-browser, exactly like the existing Blocks pipeline. Python and C++ get read-only, illustrative previews only -- see "Non-goals" below.

## Why `contracts/robot-api` isn't reused

`robot-api` (v0-v3) is a documented JSON message protocol, but it's fundamentally robot-kind-specific -- `v3/schema.json` hardcodes `arm_command`/`arm_state` with a fixed `joint: integer 0..3`; nothing resembling `{actuator_id: string, value: number}` exists anywhere in it. It's also not the live transport for anything today: `ProgramRunner` (`apps/studio/src/program/ProgramRunner.ts`) calls the WASM engine directly, and the real Python path goes through an ad hoc sidecar RPC with its own hardcoded method names (`runtime/python/okrobo/sidecar.py`/`worker.py`). Extending it for an arbitrary built robot would mean bolting a generic `{id, value}` shape onto a protocol built entirely around fixed fields, and one nothing here actually transports over. `BuiltRobotApi` is a plain in-process TypeScript interface instead, matching how `RobotApi` itself already works.

## Verified Blockly dynamic-dropdown mechanics

Checked against the installed `blockly@13.2.1` package (`node_modules/blockly/core/field_dropdown.d.ts`):

- `FieldDropdownFromJsonConfig.options` is typed `MenuOption[]` only -- `Blockly.defineBlocksWithJsonArray` (what every other block in `okroboBlocks.ts` uses) has no path to a dynamic dropdown. `okrobo_built_set_actuator`/`okrobo_built_read_sensor` are the first two blocks in this codebase defined imperatively (`Blockly.Blocks[type] = { init() {...} }`), passing a `MenuGeneratorFunction` straight into `new Blockly.FieldDropdown(fn)` -- its constructor accepts `MenuGenerator = MenuOption[] | MenuGeneratorFunction` directly.
- The generator function is re-invoked fresh every time the dropdown opens, so sourcing it from a small module-level mutable list (`setBuiltRobotFields`, called once before the Blockly workspace mounts) is correct. Test mode only ever has one Blockly workspace live at a time, so a module-level list -- not a per-workspace closure, which the JSON block style has no mechanism for anyway -- is the simplest correct mechanism.
- `validateOptions` throws on an empty options array, and runs synchronously at field construction. Build mode has no joint/actuator-authoring UI yet, so a freshly-built robot with zero actuators/sensors is the *common* case, not an edge case -- both generator functions fall back to a placeholder tuple (`["(no actuators)", ""]` / `["(no sensors)", ""]`) when the list is empty, and every codegen path treats an empty-string id as a no-op/`0` rather than an error, since the student didn't choose an invalid id -- there was simply nothing to choose.

## Why `BlocksRobotKind` is a separate type from `RobotKind`

`RobotKind` (`"car"|"arm"|"drone"`) is used well beyond Blockly: `App.tsx`'s Simulate-mode robot picker, `LessonsPanel.tsx`, and `packs/lesson.ts`'s `Lesson.robot` (pack content) -- none of which can ever target a built robot. Widening `RobotKind` itself to include `"built"` would force a dead case into every one of those `Record<RobotKind, ...>` maps and the lesson-pack schema. `BlocksRobotKind = RobotKind | "built"` is used only by Blockly-facing signatures (`BlocksPanel`'s prop, `toolboxFor`/`starterWorkspace`/`generatePython`/`generateCpp`); `RECEIVER_BY_ROBOT`/`CPP_INCLUDE_BY_ROBOT`/`CPP_MAIN_BY_ROBOT`/`PYTHON_HEADERS` stay `Record<RobotKind, string>` untouched, with `generatePython`/`generateCpp` special-casing `robot === "built"` inline instead.

## Why `setBuiltRobotFields` is called in the render body, not a `useEffect`

It must run before `BlocksPanel`'s own mount effect calls `Blockly.inject` (which renders the flyout's block previews immediately on inject, including the imperative blocks' dropdowns). A parent `useEffect` in `BuilderPanel.tsx` would run *after* the child's mount effect and lose that race -- the same ordering hazard `BlocksPanel.tsx`'s own `initialWorkspace` doc comment already flags for a related reason. The call (`apps/studio/src/builder/BuilderPanel.tsx`) is a plain, idempotent module-variable write, safe to repeat on every render and under React StrictMode's double-render.

## Why `wait()` needs no fullSteps/remainder split, unlike `ProgramRunner.move()`

`ProgramRunner.move()` precomputes `Math.floor(duration/dt)` full steps plus an exact final partial step, because the Car/Arm/Drone kinematic model cares about landing on an *exact* distance (a `forward(0.1)` should move exactly 0.1m, not 0.1m plus one frame's worth of drift). A built robot's `wait(seconds)` has no distance to be exact about -- it only needs to let simulated time pass -- so `BuiltProgramRunner` just counts down `remaining -= dt` each `tick(dt)` call, resolving once `remaining <= 0`. This does mean a `wait()` can overshoot by up to one frame (~10ms at the studio's fixed `STEP_DT`), an accepted, imperceptible rounding difference matching how `EngineBuiltRobot`'s own physics stepping already accumulates comparably small floating-point error elsewhere.

## `abort()`/`stop()` zero every actuator -- what that means depends on the actuator's own MJCF mapping, not a generic "freeze"

`built_robot.cpp` maps `robot-def`'s five actuator types to three different MJCF elements (see `docs/decisions/robot-builder-physics.md`): `motor`/`force`/`torque` -> `<motor>` (ctrl is a direct force/torque -- zero is genuinely passive), `velocity` -> `<velocity>` (ctrl is a target velocity -- zero is genuinely "stop"), `servo` -> `<position>` (ctrl is a *target angle* -- zero drives the joint toward 0 rad, which is real, visible motion if the joint wasn't already there). `BuiltProgramRunner.abort()`/`.stop()` set every actuator's ctrl to 0 uniformly; for a `servo` actuator this is "return to the neutral pose," not "freeze in place." Found empirically while writing `BuiltProgramRunner.test.ts`'s own abort test (a first draft assumed "stop" meant "no further motion" and failed against a real compiled WASM run) -- fixed by asserting the physically correct behavior (the joint settles back near 0 rad) instead of the wrong assumption. Not treated as a bug: it is the honest consequence of reusing `<position>`'s own MJCF semantics rather than inventing a robot-def concept ("hold current position") the schema doesn't have.

## Non-goals

- **No Python/C++ execution.** Both tabs in the Test-mode program drawer are read-only, illustrative previews only (`generatePython`/`generateCpp`'s `"built"` branch) -- no `okrobo.BuiltRobot` package, no `engine/api/built_robot.hpp` SDK, no sidecar wiring. Unlike the Car's own Python/C++ previews (which mirror a *real* package/header), the built-robot previews say so explicitly in their placeholder note. Real execution needs its own RPC/worker plumbing (see `runtime/python/okrobo/sidecar.py`) -- meaningfully bigger scope than this phase's in-browser Blocks path, and a future phase's work.
- **No slider/program interlock.** `ActuatorPanel`'s sliders (Phase 3) and a running program both call `EngineBuiltRobot.setActuatorCtrl` on the same underlying array; whichever fires last wins. An accepted rough edge for this foundation slice, not a bug.
- **No per-actuator value-range hint on the block's number field.** `ActuatorPanel.tsx`'s `rangeFor` computes a sensible min/max for its slider from the actuator's own limits; the Blockly field stays a plain, unrestricted number. Future polish.
- **No collapsible/resizable drawer, no persisted program per document.** The drawer is always visible in Test mode at a fixed 240px height; the program (like the rest of Test mode) resets on every Test-mode entry, consistent with the "nothing here writes back to the document" boundary Phase 3 already established.
- **No e2e coverage of non-empty actuator/sensor dropdowns.** Build mode still has no joint/actuator-authoring UI (an accepted gap since Phase 3/4), so the browser e2e check's Test-mode robot always has zero actuators/sensors -- real `set()`/`read()` numeric behavior against a real actuator/sensor is proven by `BuiltProgramRunner.test.ts` against the real compiled WASM instead. The e2e check does, for free, cover the empty-dropdown placeholder-fallback path described above.
