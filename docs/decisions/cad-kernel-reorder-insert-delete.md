# Decision: CAD Kernel — Phase 7.4 (reorder/insert/delete)

**Date:** 2026-09-07

## Scope

The last sub-phase of the Phase 7 roadmap laid out in `cad-kernel-feature-tree-data-model.md`: "reorder and insert/delete a step at any position, not just the tail." Every row in the Construction history panel can now move up/down (modifier rows only -- the root always stays feature 0), be permanently deleted (modifier rows only), and any row (root included) can have a brand-new step inserted right after it -- any position, not only the tail. Combined with Phase 7.3's edit-any-step, the feature tree is now genuinely reorderable, exactly as the user chose when picking the most ambitious of the three Phase 7 scopes originally presented.

## No contract change needed

Delete, move, and insert are all just operations on the existing `Feature[]` array -- filter out an index, swap two adjacent entries, splice in a new one. `contracts/robot-def` v2 (Phase 7.1) already allows any `Feature` in any order; nothing about the persisted shape changes this phase. This is the one CAD Kernel sub-phase since 7.1 that touches zero contract/Python/C++ code.

## One shared core, four operations: `recomputeFeatureStep.ts`

`recomputeFeatureStep.ts` (Phase 7.3) already had the right shape: build a candidate `Feature[]`, call `replayFeatures` (the whole chain, off the main thread via cadClient.ts), and on success replace the body's own `visual`/`collision`/`features` with the result -- on failure, return `{ok: false, message}` instead of throwing, carrying `executor.ts`'s own step-attributed message (`withStepContext`, Phase 7.2) verbatim. That "build a candidate, replay, commit-or-report" core is now factored out as a private `recomputeFeatures` helper, with four thin public callers:

- `recomputeFeatureStep(robot, bodyId, stepIndex, nextFeature)` -- replace (Phase 7.3, unchanged).
- `deleteFeatureStep(robot, bodyId, stepIndex)` -- filters the index out. Refuses `stepIndex === 0` (the root): there both trivially remains nothing to replay from, and removing an entire CAD history is already the Body Inspector's own separate "change to box" escape hatch, not something this phase's own delete button reaches for.
- `moveFeatureStep(robot, bodyId, index, direction)` -- swaps `index` with its immediate neighbor in `direction`. Refuses moving the root, and refuses moving anything INTO the root's own slot (index 1's "up" and the last step's "down" are both refused) -- the root always stays feature 0.
- `insertFeatureStep(robot, bodyId, afterIndex, newFeature)` -- splices `newFeature` in right after `afterIndex` (0 through `features.length - 1`, covering the root through the current tail) and replays.

All four share the exact same commit-or-real-error posture; none of this phase's own new UI needed to reinvent that logic.

## Insert reuses the executor's own prefix-replay, unchanged from Phase 7.3

A brand-new fillet_chamfer/shell/draft step needs to pick edges/faces off the shape as it will exist right where it's being inserted -- exactly the same problem Phase 7.3's edit-mode already solved with `previewEdgesAtStep`/`previewFacesAtStep` (replay `features.slice(0, stepIndex)`). Insert just calls the identical functions with `stepIndex = afterIndex + 1` (the prefix INCLUDING everything up through the insertion point, since the new step operates on that resulting shape) -- no new executor code needed this phase.

## The shared `editing` prop convention grows a sibling: `inserting`

Every one of the 5 modifier creators/editors that can meaningfully be inserted as a NEW step (CadFilletChamferEditor, CadFacePickEditor for Shell/Draft, and all 3 Cut creators) gained a parallel optional `inserting?: {afterIndex, allFeatures, onApply}` prop -- structurally identical to `editing` minus the `feature`/`stepIndex` (there's no existing feature to seed a draft from; insert-mode drafts start from the exact same defaults create-mode already uses). Internally each component now branches three ways instead of two (`editing ? ... : inserting ? ... : /* create */ ...`): picks/preview come from the prefix-replay functions at `afterIndex + 1`, the live preview always calls `replayFeatures` on the whole array with the new feature spliced in (never an isolated single-op call -- the same "preview must reflect the WHOLE chain" principle Phase 7.3 established and self-corrected for), and Apply calls `inserting.onApply(builtFeature)` instead of `replaceBodyGeometry`. The 2 Boss root creators and `CadPrimitiveRootEditor` (box/cylinder root) got no `inserting` prop -- a root is never insertable, it's always fixed at feature 0 once the body exists.

## Why a root can never be inserted, deleted, or reordered

The root (index 0) is the ONLY feature kind that creates a body from nothing (box/cylinder/extrude/revolve/loft) -- every modifier (cut/fillet_chamfer/shell/draft) needs a previous shape to act on. Allowing the root to move, or a new root-kind feature to be spliced in anywhere but position 0, would mean replaying a features list that starts with a modifier and nothing to modify -- structurally invalid, not just inadvisable. `deleteFeatureStep`/`moveFeatureStep` both refuse to touch index 0 (and refuse to move anything INTO it); `FeatureTreeList`'s own UI never offers a move/delete button on the root row at all, only its own "Insert step" affordance (a root row CAN have something inserted right after it, at position 1 -- it just can never itself be moved, deleted, or replaced by a root-kind insert).

## New UI in `FeatureTreeList.tsx`: move/delete inline, insert via a kind menu

Every modifier row grew inline ↑/↓ (disabled at either boundary of the modifier range) and a two-click-confirm Delete button, mirroring `BodyInspector`'s own existing "Delete body" confirm convention exactly. Every row (root included) grew a "+ Insert step" button that expands into a small menu of the six insertable kinds -- Fillet/Chamfer, Shell, Draft, Extruded Cut, Revolved Cut, Boundary Cut -- deliberately the exact same six labels the toolbar's own standalone tools already use, so this is the same vocabulary the student already knows, not a second one. Choosing a kind bubbles one event up (`onInsertStep(afterIndex, kind)`); the menu itself is local, ephemeral UI state owned entirely by `FeatureTreeList`, never lifted.

Move and delete act directly from this list with no separate editor panel involved at all -- unlike edit (7.3) and insert (this phase), which both replace the whole inspector with a dedicated panel while committing. Because of that, they needed their OWN pending/error state (`treeActionPending`/`treeActionError` in `BuilderPanel.tsx`) rather than reusing `editingStep`/`insertingStep`'s own `recomputing`/`recomputeError` (which are scoped to whichever editor panel is currently open -- neither is, during a plain move/delete click). A stale error from a failed move/delete on one body is explicitly cleared (`selectBody`, wrapping every user-driven body-selection path) the moment a different body is selected, so it can never misleadingly linger attached to a different body's own Construction history panel.

## Why every "does this reorder/insert/delete actually succeed" e2e check uses Cut, never Shell/Draft/Fillet-Chamfer

Phase 7.3's own e2e section already empirically reconfirmed (see `cad-kernel-edit-any-step.md`) that a pick's match tolerance is a tiny fraction of the shape's own bounding-box diagonal -- genuinely fragile to any edit that moves the picked geometry along the axis the pick depends on. Reordering compounds this risk further: swapping two picking operations changes WHICH prefix geometry each one's own recorded point must resolve against, not just how a single root's dimensions changed. Rather than gamble on which specific pair of Shell/Draft/Fillet-Chamfer picks would or wouldn't survive a swap (a real, but orthogonal, question already owned by the tolerance limitation above), `scripts/lib/studio-e2e-check.mjs`'s own reorder/insert/delete section deliberately inserts, reorders, and deletes two **Cut** steps instead: a cut carries no picks at all (`executor.ts`'s own `applyCut` always returns `resolvedPicks: []`), and set-difference is commutative regardless of overlap (`A - B - C == A - C - B`, always) -- so reordering or deleting a cut is mathematically guaranteed safe, isolating the check to the reorder/insert/delete MECHANISM itself, independent of the picks-tolerance question Phase 7.3's own section already owns and documents.

## The real bug real-browser E2E caught: `editing`/`inserting` as an unstable `useCadPreview` dep

The insert-mode e2e checks were initially flaky in a way that looked exactly like "just slow" -- Apply's own enable condition timed out unpredictably, at different steps on different runs, and bumping the timeout (10s -> 20s -> 30s -> 45s, matching the extrude cold-WASM-load precedent) never reliably fixed it. Timed diagnostics ruled out "genuinely stuck" (`.cad-status` was never a terminal error) and pointed at something structural instead.

The real cause: every one of the 5 modifier creator/editor components' `useCadPreview` call had `editing`/`inserting` (the WHOLE prop object) in its dependency array. `BuilderPanel.tsx` constructs that object fresh, inline, at each of its ~15 JSX call sites, on every one of its own renders -- an entirely ordinary-looking prop literal, not obviously a bug. But `useCadPreview`'s own effect (Phase 3) fires on ANY dependency reference change, and each SUCCESSFUL preview resolution calls `onPreviewChange` (`setCadPreview` in `BuilderPanel`), which triggers exactly one more `BuilderPanel` render -- reconstructing `editing`/`inserting` with a new identity -- which re-fires the SAME `useCadPreview` effect, restarting its debounce and discarding the just-finished computation, right as it would otherwise have gone "ready". The result was a self-sustaining loop: recompute, resolve, re-render, recompute again, forever -- with `status` only ever "ready" for the fraction of a render cycle between the resolving commit and the cascading re-render triggered by its own success. For a fast single-op preview (Phase 3's edit mode, replaying 2-3 features) that window still lands often enough for a 300ms poll to usually catch it. For insert mode's own longer chains (3-4 features, real boolean cuts) each loop iteration takes long enough that FEWER iterations fit inside any given timeout, and the poll's odds of landing inside that vanishing "ready" window drop accordingly -- exactly the load-and-length-dependent flakiness observed.

Fixed everywhere at once (all 5 components, both `editing` and `inserting`, and every derived `useCadPreview`-family hook -- `edgesPreview`/`facesPreview` too): depend on `editing`/`inserting`'s own STABLE inner fields (`editing?.feature`, `editing?.stepIndex`, `editing?.allFeatures`, `inserting?.afterIndex`, `inserting?.allFeatures`) instead of the wrapper object itself. Those inner values are all ultimately derived from `robot.bodies.find(...)` and array indexing off the stable `robot` prop, so they keep the SAME reference across an otherwise-idle re-render -- the effect now only re-fires when something has genuinely changed. This was a **latent bug since Phase 7.3** (the exact same unstable-object pattern already existed for `editing` there) that simply never had a long enough compute window to manifest until insert mode's own multi-step chains made the "ready" window rare enough to reliably miss. Confirmed fixed via two independent full real-browser E2E runs, back to back, both green with no diagnostic instrumentation left in place.

## Non-goals

- **No drag-and-drop reordering.** Move is ↑/↓ one step at a time, not an arbitrary drop target -- simpler, and every position is still reachable via repeated clicks.
- **No inserting or reordering a root.** See above -- structurally invalid, not merely restricted.
- **No new executor primitive.** Insert reuses Phase 7.3's `previewEdgesAtStep`/`previewFacesAtStep` verbatim; delete/move/insert all reuse `replayFeatures` verbatim.
- **No contract/Python/C++ change.** Confirmed by `npm run build`'s own module count and WASM asset sizes being unchanged from Phase 7.3's build.
