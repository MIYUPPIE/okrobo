# Decision: CAD Kernel — Phase 1 (Foundation)

**Date:** 2026-09-05

## Choice

Adopt a real, industry-standard B-rep CAD kernel — [replicad](https://github.com/sgenoud/replicad) (MIT), a high-level wrapper around `opencascade.js` (the WASM port of OpenCascade, LGPL-2.1) — as the foundation for Build mode's eventual Extruded/Revolved/Boundary Boss & Cut, Chamfer, Draft, Shell, and Fillet operations. This phase ships only the first vertical slice: a real sketch → extrude → mesh pipeline, a new `cad_mesh` geometry variant that renders in three.js and collides in MuJoCo, and one offline-authored example — with **no sketch UI and no Build-mode changes at all**. The remaining six phases (Sketch UI, Revolve+Boundary, Cut, Fillet+Chamfer, Shell+Draft, a live feature tree) are scoped but not started.

## `contracts/robot-def` forks to `v1` — this really is a frozen contract, unlike `pack.json`

`contracts/robot-def/v0/contract.md` states its versioning policy explicitly: frozen once all three language mirrors ship against it, with changes going to `v1/` in the same commit. That's a real, stated policy — unlike `contracts/pack/v0/pack.json`, which had no such policy and was extended in place for Robot Builder Phase 8. A new `Geometry` variant is a genuine schema addition, so `contracts/robot-def/v1/` was forked (schema + contract.md + copied-forward examples/invalid fixtures), and all three mirrors (`apps/studio/src/contracts/robotDef.ts`, `runtime/python/okrobo/robot_def.py`, `engine/src/robot_def.{hpp,cpp}`) moved to it in this same phase, mirroring the `robot-api` v0→v1→v2→v3 precedent. `v0` stays exactly as it was, a historical reference nothing points at anymore.

## `cad_mesh` is baked, frozen data — not a live feature tree

`{ type: "cad_mesh", vertices: number[], faces: number[] }` is a flat, triangulated mesh in the body's own frame — directly what both replicad's `.mesh()` output and MuJoCo's `uservert`/`userface` want, with no conversion step. This phase does not persist the sketch/extrude steps that produced it: a `cad_mesh` body is authored once (by an offline script, not a UI) and becomes ordinary static data, exactly like a hand-authored `box`/`cylinder` body already is. A live, re-editable, reorderable feature tree is Phase 7's job — editing a `cad_mesh` body today means re-running the authoring script, not adjusting a parameter in the app.

## The MuJoCo mesh-collider technique — empirically verified, not assumed

The real risk in this whole initiative was getting a physics-collidable mesh into MuJoCo's WASM build with no filesystem. Research flagged the STL-decoder-plugin/VFS-file path as carrying an unverified static-linking risk in this Emscripten build. Instead, `engine/src/built_robot.cpp:371` (`mj_parseXMLString`) and `:375`-equivalent (`mj_compile`) are two genuinely separate steps against the same `mjSpec*` — confirmed by reading `tools/mujoco/include/mujoco/mujoco.h`/`mjspec.h`, then proven with a native scratch C++ program (compiled via `g++` against `tools/mujoco/build-native/lib/libmujoco.a`) that called `mjs_addMesh(spec, nullptr)` + `mjs_setName(mesh->element, name)` + `mjs_setFloat(mesh->uservert, floatArray, size)` + `mjs_setInt(mesh->userface, intArray, size)` between those two calls, with **no `<asset>` block in the XML at all**. Output: `COMPILE OK: nmesh=1 nbody=2 ngeom=1`, exact vertex/face counts matching the hand-built tetrahedron supplied. `AddCadMesh` in `built_robot.cpp` is that exact technique, now shipping — and its own gate test (`TestCadMeshBodySettles`, `engine/tests/test_built_robot.cpp`) drops a hand-authored 8-vertex/12-face box mesh under real gravity and asserts it settles at the same resting height (0.04 m) a native `GeometryType::kBox` of the same size would — proof the collider is a real convex hull from the mesh data, not a placeholder (which would settle at the wrong height, `kMeshPlaceholderHalfExtent` = 0.03 m). The settled lateral position needed a looser tolerance (1e-3, not the box test's 1e-6): a mesh's convex-hull-derived contacts carry tiny floating-point asymmetry an analytic primitive doesn't, real but physically negligible.

`cad_mesh` support was extended to world-def objects too (`worldDef.ts`, `world_def.py`, `world_def.cpp`, and `built_robot.cpp`'s world-object geom loop, naming its mesh asset `cad_world_{id}`), not just robot bodies. This wasn't optional: `world_def.cpp`'s own `GeometryToJson`/`GeometryIsValid` switches (and `worldDef.ts`'s, and `built_robot.cpp`'s `MjcfGeomAttrs`) all reuse `robot_def.hpp`'s `GeometryType` enum directly, and every one of those switches compiles under `-Werror` with no `default:` case — adding `kCadMesh` to the shared enum forced a real decision at every one of them, the same way TypeScript's exhaustiveness checking already forced `BodyInspector.tsx`/`robotThree.ts`/`worldDef.ts` earlier in this phase. `MjcfGeomAttrs` itself throws if reached with `kCadMesh` (its `{type, size}` shape can't express a mesh reference); both call sites (`AppendGeom` for bodies, the world-object loop) special-case `kCadMesh` before ever calling it.

## `replicad`/`opencascade.js` stays out of the main app bundle — a real Worker entry point, unused this phase

The kernel's WASM (`replicad_single.wasm`, ~23 MB uncompressed) is far too heavy to load into every student's session unconditionally. `apps/studio/src/cad/kernel.ts` holds the actual sketch/extrude/mesh logic, portable to both plain Node and a browser Worker. `apps/studio/src/cad/worker.ts` is a real, ready `comlink`-exposed Worker entry point for a future Build-mode UI to construct off the main thread — but nothing in this app's import graph reaches `src/cad/*` yet (confirmed: `npm run build`'s output chunk list has no trace of replicad/opencascade), so it costs today's students nothing. `apps/studio/src/cad/extrude.ts` — the plan's promised public API (`extrudeRectangle({width,height,depth})`) — calls `kernel.ts` directly rather than routing through `worker.ts`'s comlink client: nothing in a running tab calls it yet, so off-main-thread isolation buys nothing today, and a direct call is what makes `extrude.ts` runnable under plain Node (the offline authoring script) and testable under vitest's `node` environment, neither of which has a browser `Worker` global. Once Phase 2's sketch UI actually calls this from a live tab, route it through `worker.ts` instead.

## `allowImportingTsExtensions`, and why the offline script imports `apps/studio/src/cad/extrude.ts` directly

`scripts/generate-cad-examples.mjs` needs to run the real kernel offline (no UI exists to author a `cad_mesh` body any other way). Node's native TypeScript support (no flag needed on this repo's Node v26) does **not** rewrite an extensionless or `.js`-suffixed specifier to a sibling `.ts` file the way `tsc`'s own `NodeNext` resolution does — confirmed empirically (`ERR_MODULE_NOT_FOUND` on both). The fix: `kernel.ts`'s two importers (`extrude.ts`, `worker.ts`) use a literal `./kernel.ts` specifier, and `apps/studio/tsconfig.json` gained `allowImportingTsExtensions` (safe project-wide — `noEmit` was already set, and it only *permits* a specifier form nothing else in the codebase uses; every other file keeps importing without extensions). The script itself then imports `../apps/studio/src/cad/extrude.ts` by its real path — the same precedent `scripts/lib/vision-parity-check.mjs` already set for `apps/studio/src/lib/vision.ts` — and Node's resolution naturally reaches `apps/studio/node_modules` (where `replicad` actually lives; this repo has no root-level `node_modules`) because that's where `kernel.ts` itself sits in the directory tree, not because of anything in the script's own location.

## The shipped example proves the pipeline for real, through all three mirrors

`scripts/generate-cad-examples.mjs` produces `contracts/robot-def/v1/examples/cad-l-bracket.json` — two real extruded slabs (a base and an upright, welded with a fixed joint) — by actually running replicad/OpenCascade, not a canned fixture. Both bodies' `transform` and their joint's `origin` carry the identical offset, matching `two-link-arm.json`'s own established convention (`body.transform` positions a body's geometry relative to its own joint frame, mirroring URDF's `<visual origin>` idiom — confirmed by re-reading that shipped fixture, not assumed). The new example round-trips cleanly through **all three** language mirrors: TypeScript's `robotDef.test.ts` picks it up automatically (it globs every file under `examples/`); Python's `test_robot_def.py` and C++'s `test_robot_def.cpp` both hardcode their example names, so `"cad-l-bracket"` was added to each list explicitly rather than left to chance.

## Non-goals

- **No sketch UI, no Extrude button, no Build-mode changes at all.** Phase 2's job.
- **No Revolve/Boundary/Cut/Fillet/Chamfer/Shell/Draft.** Phases 3–6.
- **No feature-tree persistence or live recompute.** Phase 7.
- **No migration of existing bodies/examples to `cad_mesh`.** Purely additive.
- **No change to the old, external-file `mesh` geometry type's placeholder behavior.** `cad_mesh` is a new, separate variant.
