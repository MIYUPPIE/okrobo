# Decision: kid-usable Blocks — easier if/else, a resizable code panel, a livelier theme

**Date:** 2026-09-10

## Scope

Three related complaints about Build/Simulate mode's own Blocks-editing experience, arriving together: "i can't use the else if at all" (with a screenshot of `controls_if`'s own mutator popup), "the code environment should be responsive and adjustable by users perfectly," and "i need the app color to be perfectly for kids... lively color for the interface."

## The real root cause behind "can't use else if at all"

Investigated directly, empirically, before assuming anything. `controls_if` is Blockly's own stock block (`src/blocks/okroboBlocks.ts`), un-customized in this codebase — no reason to suspect a library bug in one of the most widely-used Blockly blocks in existence. Measured the actual DOM instead: `.blocks-editor`'s real `getBoundingClientRect()` in a live browser showed ~188px of visible content height, after the code-tabs strip — because `.studio`'s own CSS grid hardcoded the entire Blocks/Python/World/Lessons/C++ panel to a flat `220px` row, regardless of window size. Blockly's mutator popup is a small, precision drag under the best of circumstances (a well-documented rough edge for young users); inside a 188px-tall pane, blocks stack up and run off-screen almost immediately. Not "Blockly is broken" — "there's nowhere near enough room."

## Part A: three ready-made if-shapes, not a mutator patch

Verified directly against the installed Blockly build (`node_modules/blockly/blocks_compressed.js`): `controls_if`'s own `saveExtraState`/`loadExtraState` serialize exactly `{ elseIfCount?, hasElse? }`, and Blockly's toolbox JSON `BlockInfo` type has a real, typed `extraState?: any` field (`node_modules/blockly/core/utils/toolbox.d.ts`). A toolbox flyout entry can seed a block with its mutator state already applied — no custom block, no mutator drag required for the two most common shapes. `COMMON_TOOLBOX_TAIL` (shared by every robot's toolbox, including Robot Builder's Test-mode `BUILT_TOOLBOX`) now offers plain `if`, `if`/`else`, and `if`/`else if`/`else` as three separate, directly-draggable blocks. The mutator gear still exists on the resulting block afterward, for a student who wants to go further.

## Part B: CSS-variable-driven panels, not more fixed pixels

Every panel dimension that was a flat pixel value (`180px` sidebar, `220px` code panel, `220px`/`300px` Build-mode hierarchy/inspector) became a CSS custom property with the *same* value as a fallback default — so nothing visually jumped for an existing user until they actually drag something. A new, small, reusable `ResizeHandle.tsx` component (a thin draggable bar between two CSS Grid tracks, `grow: "up"|"down"|"left"|"right"` capturing which side of the panel it's attached to) writes the live size directly to `document.documentElement.style` during drag — not React state — so dragging is smooth and doesn't re-render the whole app on every `pointermove`, the same way a browser's own native panel splitters work. The final size persists to `localStorage` on release.

The code panel's own CSS default is `max(220px, 35vh)` — genuinely responsive to window size (a real `vh` unit recalculates on every browser resize, no JS involved), while never regressing below the old fixed height on a small window. Found this floor was necessary, not decorative: headless Chrome's own *default* window (no `--window-size` flag) is only ~780×437 — at that height, a naive `35vh` alone (≈153px) would have been *worse* than the pre-existing `220px`, an actual regression on a real if unusually short screen, caught by this feature's own new e2e check before it shipped.

## A real, repeatable gotcha closed once and for all: `localStorage` in tests

`ResizeHandle` talks to the real `localStorage` global directly (a plain per-viewer UI preference, not the kind of app data `projects/webStore.ts`/`compete/runHistory.ts` inject a store for). Rendering it inside `BuilderPanel.test.tsx` crashed ~73 unrelated tests instantly: this repo's Node+vitest+jsdom combination doesn't provide a working `localStorage` (Node's own built-in Web Storage implementation returns `undefined` unless launched with `--localstorage-file`), a gotcha that had already been hit and separately worked around three times this session (`webStore.test.ts`, `compete/runHistory.test.ts`, both via per-function dependency injection). Rather than a fourth one-off workaround, `src/testSetup.ts` (loaded for every test file already) now installs a small in-memory polyfill once, globally, cleared before every test — closing this permanently for any future component that touches `localStorage` without needing to know about the gotcha at all.

## A real, self-inflicted e2e bug found and fixed: leftover resize state breaking unrelated tests

The first version of the new e2e check dragged the code panel handle up 200px to prove resizing works, then reloaded to prove persistence — and never reset it. That resize *persisted in localStorage for the rest of the browser session*, silently squeezing the sidebar/viewport enough that later, *unrelated* coordinate-based clicks (`page.clickText`, not `evalClickText`) in the Arm/Drone-switching sections much further down the same script started missing their targets — a real, reproducible cascade of unrelated failures traced back to one un-cleaned-up test. Fixed two ways: a smaller, less disruptive drag delta (80px, not 200px), and an explicit `localStorage.removeItem` + reload immediately after the persistence check, restoring the default layout before the rest of the script runs.

## Part C: a livelier palette, kept dark

The dark base stays — a bright light theme would wash out the 3D viewport's own object colours, and it wasn't the base that read as dull, it was the flat, near-monochrome *chrome*. `--accent`/`--green` got more saturated; two new named variables (`--error`, `--warning`) replaced ad-hoc hex literals scattered across the file (`#ff7a7a` × 15, `#e8b34a` × 1, `#4caf50` × 2 — the last of these two were things *this session itself* introduced for the run-history feature, using the literal hex instead of the already-existing `--green` variable, a real inconsistency caught while doing this pass, not assumed). Each robot (Car/Arm/Drone/Built robot) gets its own real accent colour on its own sidebar row, instead of one blue for everything — the same category-colour idea Scratch's own block palette uses to read as lively rather than uniform. Border radii (34 occurrences of a uniform `6px`, used almost everywhere in the app) bumped to `8px` in one coordinated sweep — safe specifically because of that uniformity, not a scattered set of individual judgment calls. The Run button — the single most-pressed control in the app — gets a solid fill instead of just a coloured outline, matching every other button.

## Verification

`apps/studio`: `npm run test` (924 passing, up from 912 — new `ResizeHandle.test.tsx`, extended `okroboBlocks.test.ts`), `npm run typecheck`, `npm run build`. `./scripts/check-studio-e2e.sh` gained a full resize-and-persist round trip (drag, confirm growth, reload, confirm persistence, clean up) plus a check that the toolbox now offers all three if-shapes in a live workspace — 3 consecutive clean runs after fixing the window-size and self-cleanup issues above. `scripts/check-studio-e2e.sh` itself now launches headless Chrome with an explicit `--window-size=1280,900` (previously unset, defaulting to an unrealistically small ~780×437 that no real user's window would match) — a real, permanent improvement to the whole suite's fidelity, not just this feature's own checks. Full `./scripts/test-all.sh` green. Manual screenshot passes confirmed: the code panel visibly grows to a genuinely usable size on a real window, dragging its handle works and survives a reload, and the toolbox's own "if / else if / else" pre-built shape renders and is directly draggable.
